# 定期実行（ルーティン）

Claude の cloud routines に登録しているプロンプトの原本。**ルーティン側を直したら、ここも同じコミットで直す。**管理画面から辿れないところで文面が変わると、何が動いているのか誰にも分からなくなる。

## 共通の前提

- どちらも **`draft: true` のまま push する。公開は人間が管理画面で行う。**自動で `draft: false` にすることは絶対にしない
- 数値の検査は形式に対してしか効かない。**もっともらしい誤った数字は、検査も人間のざっと見も通り抜ける。**だから公開を人手に残している
- コネクタは付けない。リポジトリへの書き込み以外の権限は不要
- モデルは Fable 5.1
- **クラウド環境は「Full」（Network access: Full）を選ぶ。**既定の「Default」は Trusted で、FRED・報道サイト・財務省・CoinGecko に届かない。10/2 の日次はこれで書けずに終わった。環境変数とセットアップスクリプトは空でよい（`npm ci` は手順の中で実行する）

## 公開の判定

この号は、人の確認を待たずに朝の定時に公開します。問題があれば人があとから非公開に戻します。
**ただし、大きな問題がありそうな号は公開せず、下書きのまま push して人の確認に回してください。**

次のどれかに当てはまる号は「大きな問題がありそう」と扱い、`--apply` を実行しません。

- 金・ドル指数・米10年債・WTI・主要な株価指数のいずれかで、**同じ定義の値**（同じ日の終値など）が出所ごとに違い、
  どれを採るか決められないのに、いずれかを記事に載せた（`fetch-indicators.py` が出した終値を採った場合は当たらない）
- 上の主要な数値を、一次データ（FRED・財務省・取引所など）でも複数の報道でも確かめられず、
  1件の要約や検索結果の抜粋だけに頼った
- 公開済みの過去の号に数値の誤りを見つけた（訂正の判断が要るため）
- 手順のどこかが失敗したまま残っている（`fetch-indicators.py` も代替手順も通らなかった、など）
- 書き終えた内容に自信が持てない点が残っている

次は「大きな問題」ではありません。記事に正直に書けていれば公開します。

- 取れなかった値を「未確認」と書いた（未確認は欠落であって誤りではない）
- 現物と先物、日中値と終値のように**定義が違う値**の差。これは食い違いではない
- 金の現物終値が決まらない。出所で割れるのが常なので、`docs/SOURCES.md` の系列（USAGOLD）で取れなければ、
  時点つきの日中値を載せて終値は「未確認」と書く。それで公開してよい

当てはまらなければ `python tools/publish-gate.py <YYYY-MM-DD> --apply` を実行します。このスクリプトも
機械で分かる条件（検査のエラー、主要指標の未確認、snapshot の欠け、発行日のずれ、`review` の欠落）を
確かめ、通らなければ「保留」と理由を出して終了コード 1 を返します。**「保留」が出たら公開しません。**
理由を直せるなら直して再実行し、直せなければ下書きのまま進めます。

迷ったら公開しないでください。下書きで出した号は人が数分で公開できますが、
誤った数字を公開すると読者の判断を誤らせます。

## 絶対に守ること

- `draft:` の行を手で書き換えないでください。公開は `tools/publish-gate.py --apply` だけで行います。雛形は draft: true で生成されます
- 数値を創作しないでください。出典が確認できない値は載せない。取れなかった指標は「未確認」と明記する
- 個別の売買推奨を書かないでください。投資助言・代理業の登録がないため、情報提供と分析にとどめます
- `git add -A` を使わないでください。作成したファイルを明示して add します（ユーザーが同じリポジトリを並行して触ることがあるため）
- コミットメッセージは日本語で、何を書いたかが分かる内容にしてください。公開状態で出した号は「公開」、下書きで出した号は「下書き」と書く

## 書き方

日次の要約を並べ直すのではなく、**個別の値動きではなく「資金がどこからどこへ移ったか」として束ね直してください。**週次の存在理由はそこにあります。

特に手を抜かないこと。

- `performance` … 雛形の25行（取得値入り）をそのまま残し、並び順も変えない。`note`（寸評）を書く。少なくとも金・銀・米2年・米10年・ドル指数・ドル円・原油・日経・BTC には必ず書く。数字だけでは何が起きたか伝わりません。「△ ◯/◯時点」と出た行は寸評に日付を、`読み取り` の行は「終値」と書かない、限月交代の行は限月を書く
- `ratioNotes` … 金/銀・金/原油・金/銅のそれぞれに一言。上がった・下がったではなく、何を意味するか（SKILL.md の型）
- `flows` … 金ETF（GLD）・銀ETF（SLV）の保有量。公式ページか複数の報道で確かめられた値だけ。確かめられなければ status: 未確認 のまま
- `moreLevels` … 銀とドル円のテクニカル・レベル。JSON の週足のレンジを根拠に使ってよい
- 本文の「来週の備え」に `### 金・銀・ドル円の焦点` を置き、3本の予想レンジを書く
- 本文の「今週の資金フロー構造」で、レシオ・建玉・ETFフロー・FOMC の織り込みを根拠として引く（サイトに数値は出るので並べ直さない）
- `tags` … 論点にした銘柄のトピック名（銀 / プラチナ / 銅 / 円建て金 / ユーロドル / 米2年債 / COT / クレジットスプレッド）を表記どおりに
- `scenarios` … bull / base / bear の3案。`trigger`（発動条件）・`chain`（因果連鎖）・`target`（価格目処）を同じ粒度で書く
- `levels` … 週末時点のテクニカル・レベル
- `bias` … 来週のスタンス
- `schedule` … 来週の予定のみ。対象期間内の日付を入れない

## 絶対に守ること

- 表（table）を使わないでください

## 休止の判定

`tools/should-run.py` が一手に引き受ける。**プロンプト側で祝日を判断させない。**言葉で書いた規則は、実行するたびに解釈が揺れる。

| 状況 | 扱い |
|---|---|
| 日本だけの祝日 | **出す**。米国市場は動いている |
| 直前の平日が米国休場 | **出さない**。扱う新しいセッションが無い |
| 土日 | 日次は出さない |
| 12/29〜1/3 | 出さない。1/4 から再開 |

「直前の平日が米国休場なら出さない」のは、単に前日が休みだからではない。**その日の号が既に最新のセッションを扱っているためである。**金曜がグッドフライデーなら、金曜の号が木曜分を扱っており、月曜に書くことは何もない。「前営業日が休場か」で判定すると、この月曜を取りこぼす。

日本の祝日表は持っていない。判定に影響しないためである。

米国の休場日は計算で出している（第n月曜、復活祭からの逆算、土日の振替）。表を持たないので、年が変わっても更新は要らない。
